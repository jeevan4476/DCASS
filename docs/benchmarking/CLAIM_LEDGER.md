# DCASS Claim Ledger

**Purpose:** single source of truth for every externally visible numerical or security claim. A claim may appear in a document only if it has a ledger row, and the row must point to a recorded artifact or explicitly label the statement as theory or design intent.

**Status vocabulary**

| Status | Meaning |
|---|---|
| `supported` | The recorded artifact supports the claim within the stated scope. |
| `qualified` | The claim is true only with the stated caveat; the caveat must travel with the claim. |
| `retracted` | Do not use. The claim is unsupported or contradicted by the artifact. |
| `theory` | A mathematical statement or design goal, not a measurement. |
| `pending-rerun` | The current evidence is insufficient; Phase 1 must record it before the claim is used. |

**Baseline:** `feature/gan-rl-pipeline` at `b4db808` (2026-10-21), the commit the Component 3 artifacts record; the RL retraining and its manifest are recorded in `C3_TRAFFIC_DETECTOR_EVALUATION.md` §7. Artifacts are under `storage/benchmarks/` unless stated otherwise, and each component writes a run manifest beside its results recording the commit, the dirty flag, the command, the seeds, the package versions, and the input and output hashes.

## Maintenance rules

1. Add a row before adding a new number to a document.
2. When an artifact is regenerated, update the row's artifact, field, command, commit, and status in the same commit as the document edit.
3. `qualified` claims must carry their caveat in every location. A caveat in a footnote does not qualify a headline table.
4. `retracted` claims must be removed or visibly marked as withdrawn; do not leave them in a "future work" or "target" column that reads as achieved.
5. Theory rows are allowed only when explicitly labeled as theory. Do not place a theory value in a measured-results column.
